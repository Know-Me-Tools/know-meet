# km-token-service (`services/livekit`)

The Know Meet token service. It issues room codes and short-lived LiveKit guest
tokens behind same-origin `/api`. It supersedes the frozen prototype
`docs/design/live/server.mjs`, which must never be deployed.

OpenSpec change: `wr03-token-service`. Acceptance: `features/wr-4-token-abuse.feature`
(`tests/release/token-abuse.spec.ts`), `features/wr-6-secret-hygiene.feature`, and
the contract in `tests/release/src/api-contract.ts`.

## Release limitation: one replica, in-memory state

Room codes and rate-limit buckets live in process memory.

- **Run exactly one replica.** A second replica would not know the first one's
  codes (guests would get 404) and would double the effective rate limit.
- **A restart drops every live code.** Guests already in a meeting stay connected,
  because LiveKit holds the room, but nobody can join a meeting created before the
  restart. The host must create a new meeting.

A shared store (for example Redis) removes both limits. It is not part of this release.

## Endpoints

| Method and path | Request | Success | Errors |
|---|---|---|---|
| `POST /api/meetings` | `{}` | 201 `{ ok: true, data: { code } }` | 400, 403, 429, 503 |
| `POST /api/token` | `{ code, name }` | 200 `{ ok: true, data: { url, token, identity, room, expiresIn } }` | 400, 403, 404, 429 |
| `GET /api/healthz` | none | 200 `{ ok: true, data: { status: "ok" } }` | none |

- `code` matches `^km-[a-z0-9]{3}-[a-z0-9]{3}$`. The service generates it from the OS
  CSPRNG with rejection sampling (no modulo bias) and stores it with an expiry.
- `POST /api/token` signs a token only for a stored, unexpired code. Any other code,
  well-formed or not, gets 404 `meeting-not-found` and nothing is signed. `room`
  equals `code`.
- `name` is 1 to 60 characters after control characters are removed and the value is
  trimmed. It becomes the participant's display name only.
- `identity` is generated by the service: a slug of the name plus 48 random bits in
  hex. Any `identity` field a client sends is ignored.
- `url` is `LIVEKIT_URL`. `expiresIn` is the configured token lifetime in seconds.
- `/api/healthz` needs no `Origin`, is not rate limited and reports nothing derived
  from configuration or secrets.

Errors are `{ ok: false, error: { code, message } }`:

| Status | `code` | When |
|---|---|---|
| 400 | `invalid-request` | Not `Content-Type: application/json`, body over 4096 bytes, not valid JSON, wrong fields, bad name |
| 403 | `forbidden-origin` | `Origin` missing, repeated, `null` or not equal to `KM_SITE_ORIGIN` |
| 404 | `meeting-not-found` | Code not issued by this service, or expired |
| 429 | `rate-limited` | Client bucket empty. `Retry-After` gives whole seconds |
| 503 | `capacity-exceeded` | `KM_MAX_STORED_CODES` live codes already stored |
| 408 | `request-timeout` | Handler exceeded `KM_REQUEST_TIMEOUT_SECONDS` |
| 500 | `internal-error` | Random source or signing failed (logged, no detail returned) |

`capacity-exceeded`, `request-timeout` and `internal-error` are additions to the
release contract in `api-contract.ts`; the release suite does not exercise them.

Every response, including errors, 404 and 405, carries `Cache-Control: no-store` and
`X-Content-Type-Options: nosniff`.

## The token

Signed HS256 with `LIVEKIT_API_SECRET` through `livekit-api` (feature `access-token`
only). The video grant is:

- `roomJoin: true` for `room` = the code, and nothing else at room level
- `canPublish`, `canSubscribe`, `canPublishData`: true
- `canUpdateOwnMetadata`: false
- no `roomCreate`, `roomList`, `roomRecord`, `roomAdmin`, `ingressAdmin`, `hidden`,
  `recorder` or `agent`

`exp` is now plus `KM_TOKEN_TTL_SECONDS`. The code refuses any lifetime above
3600 seconds at startup. LiveKit refreshes the token of a connected participant
itself, so a short lifetime only limits how long an unused token can be replayed.

### Participant cap and empty-room timeout

The token carries a `roomConfig` with `maxParticipants` = `KM_ROOM_MAX_PARTICIPANTS`
and `emptyTimeout` = `departureTimeout` = `KM_ROOM_EMPTY_TIMEOUT_SECONDS`. LiveKit
applies a token's room configuration when that join creates the room; it does not
change a room that already exists. Rooms here are only ever created by the first
guest's join, so the first token's values apply.

Not verified against LiveKit Cloud yet: that the project allows rooms to be
auto-created on join, and that Cloud honours the token's `roomConfig`. Until the
boundary run proves it, also set a participant cap and timeouts in the LiveKit Cloud
project as a backstop.

## Abuse controls

Both POST endpoints run the same gate, in this order:

1. **Origin.** Exactly one `Origin` header equal to `KM_SITE_ORIGIN`. Refused requests
   cost no rate-limit token. This stops other sites from using a visitor's browser.
   It is not authentication: a non-browser client can send any `Origin`.
2. **Rate limit.** One token bucket per client address, shared by both POST
   endpoints. A full bucket holds `KM_RATE_LIMIT_BURST` requests and an empty bucket
   refills completely in `KM_RATE_LIMIT_REFILL_SECONDS`, continuously (steady rate
   `burst / refill` per second). IPv6 clients are keyed on their /64. At most
   100,000 buckets are held; when the table is full of buckets that are still
   refilling, new clients get 429 rather than growing memory.
3. **Content type** `application/json`. This also forces a CORS preflight for any
   cross-site browser request, and the service never answers one.
4. **Body size** at most 4096 bytes.

Every handler, including reading the body, is bounded by `KM_REQUEST_TIMEOUT_SECONDS`.
Header-read timeouts are not configurable in `axum::serve`; the Gateway's own
timeouts cover slow clients before they reach the service.

### Room-code guessing

There are 36^6 (about 2.18 billion) codes. A guess costs one token from the
guesser's bucket. With the defaults (burst 10, refill 60 s) one address gets about
14,400 guesses a day. The risk scales with the number of codes actually live: with
10,000 live codes that is roughly a 6.6% chance per address per day of hitting some
live meeting; with the store full at the default 100,000 it is about 48%. An attacker
with many addresses scales that linearly. `KM_MAX_STORED_CODES` was raised to 100,000
so that filling the store takes about 2,000 addresses at the per-address caps (security
review R1); the cost is this higher guessing ceiling once that many codes are live.
Keep `KM_CODE_TTL_SECONDS` as low as the product allows, and watch for
`request_refused` events with code `meeting-not-found` in volume.

### Client address behind the Gateway

The service sits behind Envoy Gateway. Each trusted proxy appends the address it
received the connection from to `X-Forwarded-For`; everything left of those
entries was written by the client and is ignored.

- `KM_TRUSTED_PROXY_HOPS = N` (required, 0 to 8): the client address is the N-th
  entry from the right of `X-Forwarded-For` (all header lines joined in order).
- `N = 0`: the TCP peer address is used and the header is ignored.
- If the header has fewer than N entries, or that entry does not parse, the TCP peer
  address is used. Behind the Gateway that peer is the Gateway, so those requests
  share one bucket. A misconfiguration fails closed: it can throttle everyone, it
  can never let a client choose its own bucket. A `forwarded_chain_too_short` or
  `forwarded_entry_unparseable` warning in the logs means `N` is wrong.

Set `N` to the number of proxies that append to `X-Forwarded-For` between the
internet and the service. For Envoy Gateway in front of the pod with no other
HTTP proxy, that is `1`. The Gateway must append the downstream address (Envoy's
default with `use_remote_address`); if a cloud load balancer in front of it also
appends, use `2`. If the load balancer is TCP-only, the Gateway must learn the
client address through the PROXY protocol, or every client shares its address.

## Configuration

Environment only. Names below; values never appear in tracked files. A missing
required variable stops the process with exit code 1 and a log line naming the
variable, never its value.

| Variable | Required | Default | Range | Meaning |
|---|---|---|---|---|
| `LIVEKIT_URL` | yes | | `wss://...` | Public LiveKit URL returned to clients |
| `LIVEKIT_API_KEY` | yes | | | Token issuer key (secret store) |
| `LIVEKIT_API_SECRET` | yes | | | Signing secret (secret store) |
| `KM_SITE_ORIGIN` | yes | | `https://host[:port]` | Exact origin POSTs must send |
| `KM_TRUSTED_PROXY_HOPS` | yes | | 0 to 8 | See "Client address behind the Gateway" |
| `KM_BIND_ADDR` | no | `0.0.0.0:8080` | | Listen address |
| `KM_TOKEN_TTL_SECONDS` | no | 600 | 60 to 3600 | Token lifetime; above 3600 refused |
| `KM_RATE_LIMIT_BURST` | no | 10 | 1 to 1000 | Bucket size per client |
| `KM_RATE_LIMIT_REFILL_SECONDS` | no | 60 | 1 to 86400 | Time to refill an empty bucket |
| `KM_CODE_TTL_SECONDS` | no | 86400 | 60 to 604800 | How long a room code accepts token requests |
| `KM_MAX_STORED_CODES` | no | 100000 | 1 to 1000000 | Live codes held before 503 |
| `KM_MAX_CODES_PER_CLIENT` | no | 5 | 1 to 10000 | Live codes one address holds that no token was issued for |
| `KM_MAX_USED_CODES_PER_CLIENT` | no | 50 | 1 to 10000 | Live codes one address holds that a token was issued for |
| `KM_REQUEST_TIMEOUT_SECONDS` | no | 10 | 1 to 60 | Per-request handler timeout |
| `KM_ROOM_MAX_PARTICIPANTS` | no | 10 | 2 to 100 | `roomConfig.maxParticipants` |
| `KM_ROOM_EMPTY_TIMEOUT_SECONDS` | no | 300 | 10 to 86400 | `roomConfig.emptyTimeout` and `departureTimeout` |
| `RUST_LOG` | no | `info` | | Log filter |

The key and secret are held in a type whose `Debug` output is redacted; neither is
ever logged or returned. `LIVEKIT_URL` is public by design.

### Release run inputs

The release suite reads the deployed limits from its own environment. Set them from
the service's configuration:

| Run input | Service variable |
|---|---|
| `KM_RELEASE_TOKEN_TTL_SECONDS` | `KM_TOKEN_TTL_SECONDS` |
| `KM_RELEASE_RATE_LIMIT_BURST` | `KM_RATE_LIMIT_BURST` (at least 2 for WR-4) |
| `KM_RELEASE_RATE_LIMIT_REFILL_SECONDS` | `KM_RATE_LIMIT_REFILL_SECONDS` |

The bucket refills continuously. WR-4's "above the limit" test sends `burst + 2`
requests back to back and expects the last three to be 429, so the refill interval
per token (`refill / burst`) must be much longer than that burst takes. Keep it at
5 seconds or more (the defaults give 6). The release suite as a whole is one client,
so every spec that calls `/api` spends the same bucket.

## Logs

JSON lines on stdout through `tracing`. One `http_request` event per request (method,
known path or `other`, status, latency) and outcome events (`meeting_created`,
`token_issued`, `request_refused` with the error code). Never logged: tokens, room
codes, names, request bodies, headers, client addresses, or any `LIVEKIT_` value.

## Runtime

- Runs as a non-root user with a read-only root filesystem: it writes no files.
- Stops on SIGTERM or Ctrl-C, finishing in-flight requests (each bounded by the
  request timeout).
- Liveness and readiness probe: `GET /api/healthz`.

## Tests

Unit tests sit beside each module. Handler tests in `tests/` drive the production
router (`build_router`) with fake credentials through `tower::ServiceExt::oneshot`.
They cover the spec scenarios and both WR-4 negative controls. Under the VLBV method
they run only at the phase boundary (`wr09-release-boundary`).
